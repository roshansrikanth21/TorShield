\begin{abstract}
We built \sys{} to answer a narrow question: can a Linux module encrypt only the traffic bound for chosen peers, without asking applications to change, and can it fail closed when an eBPF classifier disappears? The current module puts the inner IP packet inside UDP, authenticates a 16-byte header with ChaCha20--Poly1305, and keeps per-peer 64-bit sequence numbers, a 1024-packet replay window, and 64-byte padding. Netfilter, a route-based L3 device, and a TC clsact program feed the same encapsulation code. We ran correctness tests in a QEMU guest on kernels 6.8.0-147 and 6.17.0-42, and throughput tests on a native WSL2 VM on 6.18.54.1. The 1\,MB IPv4 and 256\,KB IPv6 TCP transfers were byte-exact; an independent verifier opened 1054/1054 tunnel frames; deleting the TC classifier blocked 8/8 local sends and 8/8 forwarded packets with no outer frames; and a 30\,s four-stream run held 3.40\,Gbit/s with flat unreclaimable memory. \sys{} protects payloads but does not itself hide who is talking. A further enhancement is to plug the outer tunnel into a Tor pluggable transport, so that the system can borrow Tor's anonymity and censorship resistance instead of claiming them. It has no handshake or forward secrecy yet.
\end{abstract}

\section{Introduction}

We started with a small experiment. Take two network namespaces, route a chosen destination through a kernel module, and see whether an unmodified \code{iperf3} client can finish a transfer while a capture on the underlay shows only UDP frames. That experiment became \sys{}. The motivation is ordinary: many hosts still run software we cannot easily modify, and TLS leaves addresses, ports, packet sizes, and timing in the clear. A module below the socket can apply one policy to every application, including old binaries and test tools.

The first prototype used a single-byte XOR. We are not going to defend it. Known plaintext recovers the byte immediately, the length does not change, and there is no integrity check. The XOR code remains in the tree only as a baseline, and we do not use its numbers. Everything below refers to the AEAD datapath.

\sys{} is not an anonymity system. It does not pad to a fixed cell size, it does not add cover traffic, and it does not hide the outer addresses or the fact that two hosts are exchanging UDP. It is also not a WireGuard replacement: keys are configured by hand, there is no handshake, and there is no forward secrecy. What it does have is a kernel path that can be switched among Netfilter, an L3 route, and TC without changing the wire format, plus a guard that drops packets when the TC classifier is gone.

Three things came out of the work. First, we have a datapath and wire format for peer-destined IPv4/IPv6 traffic: ChaCha20--Poly1305, a 32-bit key identifier, 64-bit per-peer sequence numbers, 64-byte padding, a 1024-packet replay window, and per-peer allowed prefixes with authenticated roaming. Second, the same wire format is used by Netfilter, a route-based L3 device, and a TC clsact/eBPF classifier, and a kernel-side guard at \code{LOCAL\_OUT}/\code{FORWARD} drops peer-destined packets when the classifier or qdisc is missing. Third, we have a measurement record from two kernel versions and a native VM, including independent AEAD verification, deletion tests, manual rekey, a rate limiter, and a 30\,s run. That record is the baseline for the next round of work.

\section{Threat Model and Scope}

\paragraph{What we protect}
The secret is the inner IP packet: its addresses, transport headers, and application data. The outer IP/UDP headers, the \code{TS} magic, the key identifier, the sequence number, ciphertext length, direction, timing, and approximate size bucket are all visible. Padding to 64-byte buckets removes exact length, not the bucket.

\paragraph{Who we consider}
We consider three attackers: a passive observer on the path; an active off-path sender that injects, replays, or mutates outer datagrams; and an unprivileged local process that can open sockets but cannot read kernel memory or configure the module. We do not defend against a compromised endpoint, a root attacker who can read keys or change the kernel, or an adversary who sees both ends of the connection.

\paragraph{What we assume}
The kernel and the module are trusted. Each peer has a 256-bit key configured out of band. Root configures the peer table and mode, and, for TC, runs the loader. The classifier is attached before the mode is switched to \code{tc}.

\paragraph{What we do not claim}
\sys{} gives confidentiality, integrity, and replay resistance for tunneled packets. It does not give anonymity, traffic-analysis resistance, protocol obfuscation, forward secrecy, automatic key agreement, per-network-namespace policy, or a general denial-of-service defense. The legacy \code{stream} mode is length-preserving and unauthenticated, and we exclude it from every security claim.

\section{Related Work}

\paragraph{Anonymity and censorship resistance}
Tor is the reference point for onion routing, and its relay network is built to hide who is talking to whom \cite{dingledine2004tor}. Pluggable transports such as obfs4 and ScrambleSuit change the observable shape of a flow \cite{obfs4,winter2013scramblesuit}; format-transforming encryption makes ciphertext look like a chosen format \cite{dyer2013fte}. Those systems solve a harder problem than ours. They try to hide that a flow is Tor, or make it resemble something else. \sys{} does neither. Traffic morphing changes sizes and timing \cite{wright2009morphing}, and Parrot showed that naive obfuscation can be fingerprinted \cite{houmansadr2013parrot}. We keep those results in mind: our 64-byte padding reduces exact-length leakage, but it does not make the traffic unobservable, and we do not describe it as obfuscation.

\paragraph{Network-layer protection}
IPsec is the standards-based answer for authenticated and encrypted IP, with a policy and key-exchange framework behind it \cite{kent2005ipsec}. WireGuard is a small kernel UDP tunnel with a Noise-based handshake, cryptokey routing, and forward secrecy \cite{donenfeld2017wireguard}. OpenVPN is a userspace TLS tunnel. \sys{} borrows the UDP/AEAD shape from WireGuard but stops at a different point. It has no handshake, it uses manually configured per-peer keys, and it exposes a transparent Netfilter path and a TC/eBPF path. We do not claim better security or better throughput than WireGuard. For production privacy, WireGuard or IPsec is the right tool.

\paragraph{Programmable packet processing}
eBPF and TC let us classify and redirect packets inside the kernel \cite{hoiland2018xdp}. We use a clsact egress program only for steering. The AEAD stays in the device's \code{ndo\_start\_xmit} because the BPF helper set cannot call the synchronous in-kernel ChaCha20/Poly1305 path. The guard is a separate Netfilter hook, and that separation is exactly where the ordering problem in Section~\ref{sec:tc} comes from.

\subsection{Wire Format and AEAD}
An outer packet looks like this:
\begin{center}
\footnotesize
\code{outer IP | UDP:4789 | 16-byte header | padded ciphertext | 16-byte tag}.
\end{center}
The 16-byte header is the AEAD associated data. It starts with the two-byte \code{TS} magic, then a version byte, a flags byte (bit~0 marks an inner IPv6 packet), a 32-bit key identifier (zero selects the legacy global PSK), and a 64-bit big-endian per-peer sequence number. The nonce is the 4-byte XOR fold of the outer source and destination addresses followed by the 8-byte sequence number. The plaintext is the complete inner IP packet, zero-padded to a multiple of 64 bytes. The inner header carries the true length, and we parse it only after authentication. The tag is 16 bytes. ChaCha20--Poly1305 follows RFC~8439 \cite{nir2018rfc8439}. We take the ChaCha20 block function from the in-kernel helper and implement Poly1305 in the module. The path is synchronous because the asynchronous crypto API cannot be called from a softirq Netfilter hook.

The outer IPv4 identification field comes from a per-packet counter. That detail matters when one large inner UDP datagram becomes several outer IP fragments: a constant zero would make fragments from different datagrams indistinguishable at reassembly. The outer UDP checksum is zero over IPv4, which is legal; the AEAD tag provides integrity.

\paragraph{Port choice}
We use 4789, the IANA VXLAN port, by default. Wireshark and similar tools may label the outer datagrams as VXLAN. That is a display heuristic, not a protocol claim: the payload is the \code{TS} header and AEAD ciphertext, not a VXLAN encapsulation. The port can be changed at module load.

\subsection{Peer Table and Cryptokey Routing}
A peer entry holds a 32-byte key, a deterministic 32-bit key identifier (full FNV-1a of the key, with zero reserved), an outer endpoint, and up to eight allowed inner prefixes. Egress picks the peer by longest-prefix match on the inner destination. Ingress looks up the peer by the wire key identifier, or by outer source for a legacy global-PSK peer, authenticates, and then checks the decrypted inner source against that peer's prefixes. A packet with a source outside the allowed set is dropped and counted. The key identifier is a selector, not an authenticator: an observer can read it, but cannot make a valid tag without the key. After authentication, a peer with a per-peer key may roam to a new outer source address, so a mobile endpoint can change addresses without a control message.

\subsection{Netfilter Datapath}
\label{sec:netfilter}
The module registers hooks per network namespace with \code{register\_pernet\_subsys}. In tunnel mode, egress runs at \code{NF\_INET\_POST\_ROUTING} with priority \code{NF\_IP\_PRI\_LAST}. It skips outer packets, link-local and loopback sources, and packets already marked by the tunnel. It looks up the peer by inner destination; if there is no peer, the packet continues unchanged. If there is a peer, the GSO path segments the super-skb into \code{gso\_size} chunks, gives each segment its own sequence number, and encapsulates each one. The original skb and each segment are released after they are copied. The hook returns \code{NF\_STOLEN}. On ingress, \code{NF\_INET\_LOCAL\_IN} runs after IP reassembly. It accepts only UDP packets to the configured port; a packet with a non-\code{TS} header is left alone. A framed packet is rate-limited if enabled, linearized, authenticated, replay-checked after authentication, ACL-checked, and re-injected with \code{netif\_rx}. In tunnel mode, any parsing, authentication, replay, ACL, or allocation failure drops the packet and increments a counter. It is never forwarded as plaintext.

A TCP SYN is clamped to an MSS of 1360 bytes for IPv4 and 1340 bytes for IPv6, so the outer packet fits a 1500-byte MTU. Large inner UDP datagrams may fragment at the outer IP layer; the receiver reassembles and then linearizes before the AEAD. The current code checks 4\,KB and 60\,KB inner datagrams.

\subsection{Hybrid L3 Device}
\code{torshield0} is an \code{ARPHRD\_NONE} L3 netdevice created with \code{ip link add ... type torshield}. It has no L2 header, no ARP, no queueing discipline, an MTU of 1360, and no GSO/TSO offloads. A route such as \code{ip route add 10.0.0.2/32 dev torshield0} sends selected prefixes into \code{ndo\_start\_xmit}, which reuses the same encapsulation functions. The outer route lookup is pinned to the underlay interface supplied as \code{IFLA\_LINK}; that pin prevents the outer route from matching the route into the device and recursing. In hybrid mode the Netfilter egress hook skips packets whose route already points at a \code{torshield} device, while other peer traffic keeps the transparent path. A TC redirect hands the device a full L2 frame, so \code{ndo\_start\_xmit} strips the link header before parsing the inner IP packet.

\subsection{TC Steering and the Fail-Closed Guard}
\label{sec:tc}
TC mode replaces routes with a clsact egress classifier on the underlay. The BPF program \code{ts\_tc\_egress} looks up the inner destination in LPM tries for IPv4 and IPv6, skips multicast and link-local traffic, and redirects a match to the \code{torshield} device ifindex stored in its \code{cfg} map. Outer frames carry mark \code{0x5454} so they are not redirected twice. If a peer matches but \code{cfg[0]} has no redirect target, the program returns \code{TC\_ACT\_SHOT}, not \code{TC\_ACT\_OK}. A matching packet must never fall through to the wire.

Classifier removal is the hard case. Netfilter \code{POST\_ROUTING} runs before TC egress. In TC mode the Netfilter egress hook is bypassed, otherwise packets would be encapsulated twice. Relying on the classifier alone would therefore be fail-open if the qdisc or program disappeared. \sys{} registers IPv4/IPv6 \code{NF\_INET\_LOCAL\_OUT} and \code{NF\_INET\_FORWARD} hooks at the first priority, both before \code{POST\_ROUTING}. For a peer-destined packet, the guard uses \code{nf\_hook\_state.out}, not \code{skb\_dst}, because \code{skb\_dst} can still describe the input route at \code{FORWARD}. It accepts only if:
\begin{enumerate}
\item the output device is a \code{torshield} device, which encapsulates in \code{ndo\_start\_xmit}; or
\item the output device still has a live TC egress classifier---a TCX program named \code{ts\_tc\_egress} in \code{dev->tcx\_egress}, or a live \code{cls\_bpf} filter in the clsact mini-Qdisc (the style the loader uses today).
\end{enumerate}
Otherwise the guard returns \code{NF\_DROP} and increments \code{tc\_guard}. A local \code{sendto()} then fails with \code{EPERM}; no clear frame reaches the underlay. The TCX branch is compile-tested only; the runtime tests use the clsact path.

The guard proves that a classifier is attached. It does not prove that the classifier's maps are complete. \code{torshield-tc attach} reads every \code{allowed=} prefix from \code{/proc/torshield/peers} and fills the LPM tries before switching the mode to \code{tc}. If a peer is added, deleted, or cleared while the mode is \code{tc}, the kernel forces the mode back to \code{tunnel} until the loader reruns. Direct map edits or a hand-loaded classifier are outside the guarantee. The loader and the peer-list update are not one atomic transaction, so operators must not reconfigure peers concurrently with \code{attach}.

\paragraph{Residual race}
The guard and the later TC egress hook read the attachment separately. If a classifier is deleted after the guard accepts a packet but before that packet reaches egress, that one in-flight packet can still leave in clear. The deletion tests in Section~\ref{sec:eval} prove fail-closed behaviour for all subsequent packets, not a zero-race guarantee. Closing this needs a last-chance \code{ndo\_start\_xmit} check or a single authoritative steering point; neither is implemented.

\subsection{Replay, Rate Limiting, and Manual Rekey}
The receiver keeps a 1024-packet sliding window per peer. Sequence zero is invalid. The window moves only after successful authentication, so an off-path packet cannot consume a slot. We chose 1024 packets because four parallel streams can reorder enough to make a 64-packet window too tight.

An optional per-source fixed-window limiter (\code{ts\_rl\_pps}, default zero) runs before \code{skb\_linearize} and Poly1305. It bounds the crypto work one source can force, but it is not a cookie challenge and the source address is spoofable. It is disabled by default so that measurements are not capped.

Per-peer keys can be rotated by hand. \code{rekey-peer} moves the current key to a previous slot and starts sending with the new key; the receiver accepts both key identifiers until \code{rekey-commit} erases the previous key. A second rotation before commit is rejected, so the oldest key cannot be silently discarded. This protects packets already in flight, but both ends must be reconfigured and traffic can drop between the two commands. There is no handshake and no forward secrecy.

\section{Implementation}
The canonical module is \code{module/LKM/torshield.c}; the TC classifier and loader are in \code{module/LKM/tc/}. The control plane is \code{/proc/torshield/\{psk,peers,mode,stats\}} with a thin \code{torshieldctl} wrapper. The peer file accepts \code{+endpoint key HEX allowed PREFIX,...} and \code{-endpoint} or \code{clear}; the stats file exposes tunnel, device, ACL, roaming, rate-limit, and guard counters. The module registers ten hooks per network namespace: six datapath hooks (IPv4/IPv6 \code{PRE\_ROUTING}, \code{POST\_ROUTING}, \code{LOCAL\_IN}) and four guard hooks (IPv4/IPv6 \code{LOCAL\_OUT}, \code{FORWARD}).

The TC loader is a libbpf program. It loads \code{torshield\_tc.o}, fills the LPM and \code{cfg} maps, attaches the program to the underlay's clsact egress, and only then writes \code{tc} to the mode file. \code{detach} writes \code{tunnel} first and then removes the qdisc. A watchdog can poll the attachment and revert the mode, but it is a recovery aid, not the security boundary.

The module builds cleanly with \code{make W=1} against Ubuntu 24.04 kernels 6.8.0-147 and 6.17.0-42, and against the native 6.18.54.1 headers used for the performance runs. The 6.16 ChaCha API change (opaque state array to \code{struct chacha\_state}) is handled with a version-conditional shim. The TC object and loader build with \code{-Wall -Wextra} clean.

\section{Evaluation}
\label{sec:eval}

\subsection{Test Bed and Method}
Correctness, deletion, and interoperability tests run in an Ubuntu 24.04 QEMU 8.2 guest with kernel 6.8.0-147 and TCG, no KVM. The guest uses network namespaces \code{n1}/\code{n2} connected by a veth pair; a third namespace \code{n3} is used for the forwarded-path test. Throughput is measured separately on the native WSL2 kernel 6.18.54.1 (Hyper-V, 16 vCPUs), because TCG CPU emulation is not a throughput measurement. The native host is a VM, not bare metal. The direct-veth baseline is about 100\,Gbit/s, so the link is not the bottleneck; the tunnel is CPU-bound.

Each run starts from a clean module, configures keys and peers, and captures outer packets. A host-side Python verifier independently reconstructs the nonce and AAD and decrypts each frame with the \code{cryptography} package. Counters are read from \code{/proc/torshield/stats}. The test harness and per-stage scripts are part of the artifact.

\subsection{Correctness and Interoperability}
Table~\ref{tab:correctness} is the raw list. The IPv4 TCP transfer was byte-exact, the IPv6 transfer was byte-exact, and the independent verifier accepted every captured frame. The large-UDP cases exercise outer fragmentation and reassembly. Replay, tamper, and unknown-source packets were dropped with exact counter increments. TC and hybrid paths used distinct inner and outer prefixes, so a successful transfer also demonstrates cryptokey routing rather than address coincidence.

\subsection{Wire-Format Check}
Independent AEAD verification accepted 1054/1054 tunnel frames, 807/807 hybrid IPv4 frames, 209/209 hybrid IPv6 frames, 210/210 TC IPv4 frames, and 68/68 TC IPv6 frames with the correct key. The TC captures accepted 0/210 and 0/68 when verified with the global PSK, which confirms that key selection is actually in use. The native IPv6 pcap capture was empty in the WSL2 harness, so the IPv6 wire claim rests on the QEMU 68/68 capture; native IPv6 was verified functionally by echo and counters.

\subsection{TC Fail-Closed Behaviour}
Table~\ref{tab:guard} reports the deletion tests. In the \code{LOCAL\_OUT} test, a local socket sends eight packets while the classifier is deleted. All eight fail with \code{EPERM}, the peer server receives zero, \code{tc\_guard} increases by eight, and both \code{dev\_out} and \code{tun\_out} remain unchanged. Deleting the clsact qdisc produces the same result. Reattaching the classifier restores a 16/16 echo; detaching falls back to the Netfilter path at 8/8.

The \code{FORWARD} test injects raw frames on \code{n1}, so the sender's \code{LOCAL\_OUT} hook is bypassed. With no classifier, \code{n2} receives eight forwarded inner packets, \code{n3} sees zero outer packets, \code{tc\_guard} increases by eight, and \code{dev\_out} does not move. With the classifier present, \code{tc\_guard} stays flat, \code{dev\_out} increases by eight, and \code{n3} records eight \code{tun\_rx}. Deleting the classifier returns to zero outer packets and a guard increase of eight. That is the empirical basis for the fail-closed claim, with the residual race noted in Section~\ref{sec:tc}.

\subsection{Manual Rekey and Rate Limiting}
On the native kernel, a rekey changed the egress key identifier from 4290739141 to 1666914373. During the grace period, four payloads using the old and new keys were all accepted. After \code{rekey-commit}, one old-key packet was rejected as non-peer traffic: \code{tun\_in} increased by four, \code{tun\_peer} by one, and \code{tun\_replay} stayed zero. A same-key no-op returned success; a second rotation before commit, a commit without a previous key, and invalid hex all returned errors without changing state.

With \code{ts\_rl\_pps=50}, 950 of 1000 synthetic packets were rejected before the AEAD and 50 reached it; a legitimate 64-packet echo still completed 64/64. That demonstrates the limiter's placement, not a general DoS defense.

\subsection{Throughput}
Table~\ref{tab:perf} reports the native VM measurements. The baseline is direct veth with four TCP streams. The tunnel is CPU-bound: one stream reaches about 0.91--0.97\,Gbit/s and four streams reach 3.02--3.35\,Gbit/s. \section{Security Analysis}

\paragraph{Protections}
The AEAD gives confidentiality and integrity for the inner IP packet, including its addresses and transport headers. The 64-bit per-peer sequence number and the 1024-packet window reject replays after authentication. The key identifier selects a per-peer key; the inner source ACL stops a peer from injecting a source prefix it does not own. Endpoint roaming happens only after authentication, so an off-path attacker cannot redirect a peer by spoofing an outer source. In tunnel and hybrid modes, every authentication and parsing failure drops the packet. In TC mode, the guard drops peer-destined packets when the classifier is missing, and the classifier itself drops a matching packet when its redirect target is unset. Padding to 64-byte buckets reduces exact-length leakage.

\paragraph{Residual risks}
Outer addresses, ports, the \code{TS} magic, key identifier, sequence number, ciphertext length, direction, timing, and approximate size bucket are visible. The system does not resist traffic analysis or DPI. There is no handshake, no forward secrecy, and no automatic key agreement; a compromised key exposes the traffic it protects, and a compromised endpoint exposes plaintext. The peer table, key, and mode are global across network namespaces. The rate limiter is a fixed-window filter, not a cookie challenge, and the source is spoofable. The TC guard has a narrow check-to-egress race; the deletion tests prove fail-closed behavior for subsequent packets, not absolute zero-race closure. The TCX path is not runtime-tested. TC and hybrid mode are prototypes, not production-hardened transports. The legacy stream mode has no integrity and is excluded.

\paragraph{Anonymity path}
\sys{} protects payloads but does not itself hide who is talking. The next enhancement is to plug the outer tunnel into a Tor pluggable transport, so that the system can borrow Tor's anonymity and censorship resistance instead of claiming them. That integration is future work; the current code has no onion routing, cover traffic, or relay network.

\section{Discussion and Lessons}
Two things stand out. First, transparency is not free: the same packet can be selected by Netfilter, a route, or TC, and the order of those mechanisms decides both correctness and failure behavior. The TC guard exists because \code{POST\_ROUTING} runs before TC egress; a fail-closed design needs a check before the point where the packet can escape. Second, replay-window sizing is a property of the deployment's parallelism, not a constant. We size the window for the most parallel test we run, and we would revisit that number for a different queue layout.

The XOR result is also a lesson. A length-preserving transform can be called ``obfuscation'' and still be trivially invertible; without authentication and a nonce discipline, it is not a security mechanism. Replacing it with an AEAD forced a different framing, a sequence number, a replay window, and a key identifier, and made the evaluation meaningful.

\section{Conclusion and Future Work}
\sys{} is a transparent in-kernel authenticated tunnel with three steering paths and a kernel-side fail-closed guard for TC. The current code is byte-exact on IPv4 and IPv6 TCP, survives independent AEAD verification, drops replay/tamper/unknown-source packets, and blocks subsequent local and forwarded packets when the TC classifier is removed. On a native VM it sustains 3.40\,Gbit/s over four streams for 30\,s with flat unreclaimable memory. The next step is to integrate the outer tunnel with a Tor pluggable transport, which would add anonymity without changing the datapath.

Future work is concrete: close the guard-to-egress race with a last-chance transmit check or a single steering point; add a handshake and forward secrecy; move the control plane to netlink and make state per-network-namespace; deliver decapsulated packets through the tunnel device so policy routing and \code{rp\_filter} see them; advertise GSO/TSO on the device and segment in the driver; run the deletion suite for IPv6 and the TCX path; repeat the throughput study on bare metal with a physical NIC; and evaluate the Tor pluggable-transport integration. Until then, \sys{} remains a research and teaching artifact, not a production replacement for WireGuard or IPsec. The code and test harness are available at \url{https://github.com/roshansrikanth21/TorShield}.
